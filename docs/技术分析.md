# 技术分析：星际争霸2 的 21:9 限制在哪

> **致谢**：本作品是在 [NGA 这篇帖子](https://bbs.nga.cn/read.php?tid=47835650) 的原创作品基础上完成的。

目标二进制：`SC2_x64.exe`。本文覆盖两个版本：

- **5.0.15.98370 / 5.0.17.98370**（`Versions\Base98370`，64,925,344 字节量级）——最初逆向的版本，
  `ImageBase = 0x140000000`，7 个节（`.text` / `.rdata` / `.data` / `.pdata` / `_RDATA` / `.rsrc` / `.reloc`）
- **5.0.17.98310**（`Versions\Base98310`，64,925,904 字节）——当前主目标，适配记录见第七节

本文记录根因、证据与重新定位的方法，供版本更新后复用。

## 一、四处根因

### 1. 分辨率下拉是写死的 17 项表（RVA `0x3BD8090`）

`.data` 中一张静态表，每项 **24 字节**：

```c
struct ResolutionEntry {      // 24 bytes
    uint32_t width;
    uint32_t height;
    const char *label_begin;  // 例：0x142BF2700 -> "@UI/480x360"
    const char *label_end;
};
```

17 项从 `480x360` 一直到 `3840x2160`，**没有任何 21:9**。

- 列表填充：`sub_141122180` —— `v3 = &off_143BD8098; while (v2 < 0x11) { ... v3 += 3; }`
- 选中回调：`sub_141121590` —— `cmp eax, 11h / jnb`，然后 `width = table[24*i]`、`height = table[24*i+4]` 写进配置

这两个函数是全二进制中**唯一**引用该表的代码。

### 2. 分辨率解析函数把宽高比上限锁死在 16:9（RVA `0x2BFC1D0`）

`sub_141181240(out_w, out_h, out_hz)` 负责把"当前显示模式"映射成一个受支持的分辨率：

```c
float ar = (float)w / (float)h;
if (w >= 1024 && h >= 720) {
    if (ar >= 1.25 && ar <= 1.7777778) {        // ← 上限常量
        if (fabs(ar - desktop_aspect) <= 0.05)  // 与桌面宽高比的偏差
            ... 选出候选 ...
    }
}
```

- 常量：`0x2BFC1D0`，float `1.7777778`（`0x3FE38E39`），**全二进制只有这一处引用**
- 桌面 3440x1440 的宽高比是 2.3889 → 所有候选被过滤 → 返回 0
- 返回 0 的后果：`sub_14114D0B0` 显示 `@UI/NoResolutionFound`；`sub_1411815E0` / `sub_141182AE0` 在应用画质预设时把分辨率重置成 1600x1200

### 3. 画质预设门槛（RVA `0x118125E`）

同一函数入口：

```asm
0x14118125C  83 FB 05        cmp  ebx, 5
0x14118125F  0F 8D ...       jge  loc_14118154F   ; preset >= 5 直接 return 0
```

自定义画质档（preset 5/6）下连解析都不做。

### 4. 窗口宽高比二次夹取（RVA `0x2C2A588`）—— 真正把窗口摁住的那一处

`sub_1413CBB50(a1, a2)` 在**窗口化全屏**下把窗口宽高比再夹一次：

```c
if (displaymode == 1) {                 // 窗口化全屏
    if (sub_1411817D0(&rect)) {         // 全局显示矩形 = 3440x1440
        a1 = rect.right - rect.left;    // 3440
        a2 = rect.bottom - rect.top;    // 1440
    }
}
...
float ar = (float)a1 / (float)a2;       // 2.3889
if (ar <= 1.7786459) { ... }
else if (ar > 1.7886459) {              // ← 常量 0x2C2A588
    ar = 1.7786459;
    if (displaymode == 1) {
        a1 = (int)(a2 * 1.7786459);     // 1440 × 1.7786459 = 2561
    }
}
...
sub_140153360(hwnd, rect)               // → MoveWindow(hwnd, 0, 0, 2561, 1440, 1)
```

`1440 × 1.7786459 = 2561.25 → 2561`，与实测窗口宽度**逐位吻合**。
这段在每次窗口尺寸变化时都会重跑，所以外部 `SetWindowPos` 一律被改回。

## 二、为什么窗口尺寸等于渲染分辨率

窗口化（含窗口化全屏）下，D3D9 呈现参数由 `sub_140CD2B60` 填充：

```c
present->BackBufferWidth  = windowed ? 0 : *(mode+32);
present->BackBufferHeight = windowed ? 0 : *(mode+36);
present->Windowed         = *(mode+16);
```

BackBuffer 宽高传 0，D3D9 取**窗口客户区**。所以把窗口钉在 3440x1440，就等于渲染 3440x1440。

`displaymode` 取值由 `sub_14114B280` 的下拉项结构（+16 偏移处即存储值）决定：

| 值 | UI 项 | 窗口几何（`sub_14010CFB0`） |
|----|-------|------------------------------|
| 0 | `@UI/Windowed` | 保存的位置 + `windowwidth`/`windowheight`，带边框 |
| 1 | `@UI/WindowedFullscreen` | 无边窗口，取当前显示矩形（桌面） |
| 2 | `@UI/FullScreen` | 无边窗口，取 `width`/`height`，走独占模式选择 |

配置变量分工：

| 变量 | 用途 |
|------|------|
| `width` / `height` | 初始窗口与全屏分辨率 |
| `windowwidth` / `windowheight` | 窗口化模式尺寸 |
| `recWidth` / `recHeight` / `recResolution` | "推荐分辨率"与表索引，**不落盘**，每次启动重新推导 |

## 三、补丁表

| 位置 | RVA | 文件偏移 | 原始 → 补丁后 |
|------|-----|----------|---------------|
| 表项 16 宽度 | `0x3BD8210` | `0x3BD7A10` | `00 0F 00 00` → `70 0D 00 00` |
| 表项 16 高度 | `0x3BD8214` | `0x3BD7A14` | `70 08 00 00` → `A0 05 00 00` |
| 标签文本 | `0x2BF2800` | `0x2BF2000` | `"@UI/3840x2160\0"` → `"3440x1440\0"` |
| 标签尾指针 | `0x3BD8220` | `0x3BD7A20` | `0x142BF280D` → `0x142BF2809` |
| 解析宽高比上限 | `0x2BFC1D0` | `0x2BFB9D0` | `1.7777778f` → `3.0f` |
| 画质预设门槛 | `0x118125E` | `0x1180A5E` | `05` → `07` |
| 窗口宽高比夹取 | `0x2C2A588` | `0x2C29D88` | `1.7886459f` → `3.0f` |

节映射：`.text` raw `0x800`，`.rdata` raw `0x2A9D800`，`.data` raw `0x3B94800`。

选择 `3.0f` 而不是更小的值，是为了同时容纳 21:9（2.389）与 32:9（3.556 会被拒），
且不改变 16:9 桌面的原有行为（0.05 容差仍会把 21:9 模式从 16:9 桌面上排除）。

## 四、取证方法

静态分析（IDA + `ida-pro-mcp`）能定位前 3 处；第 4 处是靠运行时证据抓出来的。

### 1. 静态

- 字符串检索：`windowwidth` / `displaymode` / `@UI/WindowedFullscreen` / `Cannot enumerate display modes`
- 交叉引用：`xrefs_to` 追配置变量对象（`qword_14507CE60` = `width`）
- 反编译：Hex-Rays 看 `sub_141181240`、`sub_141122180`、`sub_1413CBB50`
- 常量检索：在 `.rdata` 里找 `0x3FE38E39`（1.7777778f）、`0x3FE4F259`（1.7886459f）

### 2. 运行时（关键）

1. 直连进程读内存，确认游戏内部状态与窗口尺寸不一致 → 说明限制在窗口层。
2. 在 `SetWindowPos` / `MoveWindow` / `SetWindowPlacement` 的 IAT 槽上装注入桩，
   记录参数与返回地址。
3. 抓到 `MoveWindow(hwnd, 0, 0, 2561, 1440, 1)`，调用点 RVA `0x15338A` → `sub_140153360`。
4. 反查其调用者 `sub_1413CBB50`，反编译即见 `1.7786459` 夹取。
5. 把常量改成 `3.0f` 后轻推窗口 → 窗口立刻变成 3440x1440 并稳定。

## 五、版本适配指南（游戏更新后怎么重新定位）

补丁是**按版本硬编码偏移**的，更新后必须重新定位。步骤：

1. **定位分辨率表**
   搜索字符串 `@UI/3840x2160`，取其地址往前推 13 字节找到 `@UI/480x360`；
   或直接搜索连续字节 `E0 01 00 00 68 01 00 00`（480x360）。
   表基址 = 最后一个标签指针 − 16 − 24×16。校验：17 项、每项 24 字节、末项 `3840x2160`。

2. **定位两个浮点常量**
   在 `.rdata` 里搜索 `39 8E E3 3F`（1.7777778f）与 `59 F2 E4 3F`（1.7886459f），
   用交叉引用确认它们分别落在"分辨率解析"和"窗口宽高比"两个函数里。

3. **定位预设门槛**
   在解析函数入口附近找 `83 F8/83 FB/83 FE 05`（`cmp reg, 5`）紧邻 `jge`。

4. **验证**
   改完后用 `status` 确认 7 处都 `patched`，再启动游戏实测窗口尺寸。

5. **兜底手段**
   如果常量地址找不到，用 `MoveWindow` IAT 钩子抓调用点（见上一节），
   反查调用者后重新定位窗口夹取常量——这是最可靠的路子。

6. **自写 capstone 引用扫描（98310 已验证可用的路线）**
   Ghidra 自动分析在本机对 66 MB 级引擎 exe 的 thunk 阶段病态缓慢
   （约 15 条/分钟，数小时不完），改用 Python + capstone 直接扫 `.text`：
   - `cs.detail = True`（拿操作数内存信息）+ `cs.skipdata = True`
     （跳过不可解码字节），8 线程分块约 9 分钟扫完 47 MB；
   - **坐标陷阱**：`cs.disasm(bytes, base)` 传入的 base 若是 RVA，
     则 `insn.address` 就是 RVA，RIP 目标 = `insn.address + insn.size + disp`
     **不要再减镜像基址**；减了就会得到「全部 0 引用」的假象
     （本项目踩过两次）。
   - `.text` 前 ~512KB 是抗反汇编垃圾字节，会产生大量假 RIP 目标，
     用目标区间（`.rdata`/`.data` RVA 范围）过滤即可。
   - 先扫常量/字符串的 8 字节指针值（数据侧间接引用），再扫 RIP 相对
     引用与 `movabs` 立即数，最后对落在 `.data` 的引用读其 8 字节
     存储值做一级指针链解析。
   另注意 98310 起导入表只剩 `user32!MessageBoxW`，窗口 API 运行时解析，
   IAT 钩子兜底要改成对 `GetProcAddress` 返回的 `MoveWindow` 打 `DR0` 断点。

## 七、98310 适配记录（5.0.17.98310）

### 1. PE 布局

`ImageBase = 0x140000000`（与 98370 相同）。**PE 入口点 = `0x00000000`（无入口）**。
关键节（vaddr → 文件偏移，常规差 `0x800`；`.data` 例外，差 `0x1000`）：

| 节 | 虚拟地址 | 备注 |
|----|----------|------|
| `.text` | `0x1000` | raw `0x800`；**整段密文**（首 4MB 熵 7.9967、中段 16K 熵 7.9972 ≈ 8.0；字节分布近均匀；deflate 解码 0 字节；压缩/7z/LZMA 魔数均无真实命中；低熵窗口（如 `0x4000`–`0x27000`，熵 6.2–7.7）逐字节反汇编后全部为垃圾指令——是密文内部的噪声，不是明文代码桩），运行时解密，见第七节 3 |
| `.rdata` | `0x2CEE000` | 只读数据，**明文**（熵 5.34），字符串/浮点常量均在此 |
| `.data` | `0x38ED000` | 可读/可写数据，**明文**；文件偏移 = RVA − `0x1000`；raw 仅 `0xE7800`，vsize `0x42BECB0`（虚拟尾部为零填充，运行时初始化） |

### 2. 已定位站点（字节校验通过）

| # | 站点 | RVA | 原始字节 | 说明 |
|---|------|-----|----------|------|
| 1 | 分辨率表项16 宽度 | `0x039209E0` | `00 0F 00 00` (3840) | 表基址 `0x03920860`，17×24 字节，与 98370 结构完全一致 |
| 2 | 分辨率表项16 高度 | `0x039209E4` | `70 08 00 00` (2160) | 同上 |
| 3 | 分辨率标签文本 | `0x02E6F760` | `"@UI/3840x2160\0"` + 3 个 NUL | 16 字节槽位，文件偏移 `0x2E6EF60` |
| 4 | 分辨率标签尾指针 | `0x039209F0` | `0x142E6F76D` | 表项16 的 label_end 字段 |

### 3. 代码引用为零的真相：`.text` 是密文（决定性发现）

98370 的三处「函数内常量/指令字节」在 98310 里**无法在磁盘文件上定位**——原因不是
扫描器问题，而是 98310 的代码段根本不以明文存在：

| 证据 | 结果 |
|------|------|
| `.text` Shannon 熵（首 4MB / 中段 16K） | `7.9967 / 7.9972` ≈ 8.0 = 纯随机；对比 `.rdata` 5.34、`.data` 4.26 |
| PE 入口点 `AddressOfEntryPoint` | `0x00000000`（无入口，无法直接执行） |
| `.pdata` 异常表（257,194 个 RUNTIME_FUNCTION，覆盖 42.2MB） | 抽样 40 个函数起点，37 个首字节为随机字节——异常表描述的是**解密后**的镜像布局 |
| `SC2.exe`（32 位同版本目录） | 同样 EP=0、`.text` 熵 7.98（32 位引擎也是密文） |
| `Support64\SC2Switcher_x64.exe`（1MB） | **明文** `.text`（熵 6.44）、EP=0——这是加载器/切换器载荷 |

**架构结论**：`SC2Switcher_x64.exe`（其导入表仅 4 个符号：
`CloseHandle`、`LoadImageW`、`GetStockObject`、`SystemFunction036`——
最后一个即 CNG 的 `BCryptDecrypt`，说明切换器/加载链使用 Windows CNG 做解密）
在运行时解密 `SC2_x64.exe` 的 `.text` 后加载运行
（数据节 `.data`/`.rdata` 为明文、原样参与加载）。推论：

- **数据段站点可在磁盘文件上修补且生效**（加载器原样拷贝明文的 `.data`/`.rdata`）
  —— 分辨率表、浮点常量、字符串全部在明文数据段，本 mod 的全部 27 处站点均在此列。
- **代码段站点无法在磁盘文件上修补**：修改密文 `.text` 的字节，解密结果不可预测
  （且解密器行为未逆向）。98370 的「预设门槛 `cmp 5` → `cmp 7`」这类指令补丁
  在 98310 上不可行；如需干预，只能走运行时路线（见第九节）。

对明文数据做的穷尽静态引用检索（全部针对磁盘文件，均 0 命中，互相印证）：

- RIP 相对引用：两种独立反汇编（4KB 重锚定线性扫描 11,501 片 + `.pdata` 函数锚定
  257,194 函数），覆盖 47.1MB，引用密度按 1MB 分块均匀（38.7万–40.9万/MB，
  无死区/失步区）——扫描器健全，0 引用为真；
- `movabs r64, imm64` 全镜像地址常量：0 命中；原始 imm32 RVA 常量：0 命中；
- `.rdata`/`.data` 中存储的 u64 指针 / u32 RVA：0 命中；
- 字符串副本（`.rsrc`、`_RDATA` 等其余节）：仅 `.rdata` 各 1 份，无第二副本；
- `"MoveWindow"` 字面量（任何编码）：全文件 0 命中；
- `cmp reg,5`（`83 F8–FD`、REX 前缀、32 位立即数全形式 + 98370 原序列
  `83 FB 05 0F 8D`）：全 `.text` 仅 13 处，其中 12 处位于真实函数（`.pdata` 映射
  校验），但**无一处**具备 98370 门槛形状（`cmp reg,5` + 紧邻 `jge rel32`、
  位于解析函数入口 +0x1C）——98310 源码很可能已移除/重构该门槛。

**勘误**：此前「双精度查找表」一节作废——`0x02FB3850..` 区域实际是一张
**nibble 排列查找表**（`F0 F1 F2 F3 …` 按 `+0x80` 周期重复），`.data` 结构
`0x03941C00–0x03941E00` 是编解码/vtable 类结构（`0x01010101` 掩码 + 指向该
nibble 表的指针），与显示/宽高比无关。此前「RIP/绝对/imm32/imm64 四种检索 0 命中」
的结论当时被归因于扫描器坐标 bug；经多轮修正后扫描（坐标已用已知数据逐字节验证）
仍 0 命中——真相是 `.text` 密文化，静态代码引用本就不存在。

**浮点上限常量（明文 `.rdata`，全部可静态修补）**：

| RVA | 值 | 98370 对应物 |
|-----|----|--------------|
| `0x02E7BC80` | `1.7777778f` | 解析上限（98370 `0x2BFC1D0` 同值） |
| `0x02FB72A0` | `1.7777778f` | 窗口夹取候选 |
| `0x02D06700` | `1.7786459f` | 98370 窗口夹取同值常量（`0x2C2A588` 同值，紧邻 `WindowedFullscreen` 字符串 `0x02D0668E`） |

三个候选全部放宽到 `maxAR+0.05`：覆盖解析上限 + 窗口夹取两条路径；若某处未被
代码引用也无害（均为 16:9 类上限常量，放宽即正确方向）。哪一处真正被引用，
以运行时解密代码扫描为准（第九节）。

### 4. 98310 补丁表（多条目设计）

**设计变更**：不再占用 `3840x2160` 那一格（表项 16 原样保留），改为覆盖低档条目
0–5（480x360 / 640x360 / 640x480 / 640x512 / 800x600 / 960x540）——这些分辨率在
5120x1440 显示器上用不到，覆盖零副作用；下拉表仍是 17 项。
每条目 4 处（宽 4B、高 4B、标签 16B、标签尾指针 8B）= 24 处 + 3 处函数点 = **27 处**。

**表条目（24 处，已对实机 exe 逐字节校验）**：

| 条目（原值 → 新值） | 宽 | 高 | 标签槽 | 标签尾指针 |
|---|---|---|---|---|
| 0（480x360 → 2560x1080） | `0x03920860` | `0x03920864` | `0x02E6F660` | `0x03920870` |
| 1（640x360 → 3440x1440） | `0x03920878` | `0x0392087C` | `0x02E6F670` | `0x03920888` |
| 2（640x480 → **5120x1440**） | `0x03920890` | `0x03920894` | `0x02E6F680` | `0x039208A0` |
| 3（640x512 → 3840x1600） | `0x039208A8` | `0x039208AC` | `0x02E6F690` | `0x039208B8` |
| 4（800x600 → 5120x2160） | `0x039208C0` | `0x039208C4` | `0x02E6F6A0` | `0x039208D0` |
| 5（960x540 → 3840x1080） | `0x039208D8` | `0x039208DC` | `0x02E6F6B0` | `0x039208E8` |

- 新标签 9 字符（如 `"2560x1080\0"`），标签尾指针 = `0x140000000 + 槽址 + 9`（指向 NUL）。
- 旧值示例：entry 0 `480x360` / `"@UI/480x360"`（11 字符）/ 尾指针 `0x142E6F66B`。
- 条目 6–15（960x768 … 1920x1200）与条目 16（3840x2160）保持原样。
- 98370 同构：条目 0–3（表基址 `0x3BD8090`、标签槽基址 `0x2BF2700`）共 16 处。

**常量点（3 处，已对实机 exe 逐字节校验）**——98310 的 27 处站点全部位于明文

## 九、运行时验证路线（`.text` 密文化后的唯一代码级手段）

磁盘文件上的静态分析已穷尽（第七节 3）。若 27 处数据站点在实机验证后仍不满足
（例如窗口夹取/解析路径走了代码内硬编码、或门槛逻辑以密文形式残留），代码级
取证只能在**游戏进程的解密内存**里做：

1. **进程识别**：`probe2.py` 自动定位游戏进程（优先按 `SC2_x64.exe` 模块基址，
   找不到则全内存扫表头 `E0 01 00 00 68 01 …` 反推镜像基址）。
2. **密文/明文核验**：读进程内 `.text` 首 1MB 算熵——文件侧 8.000，进程侧应
   显著下降（已解密）。
3. **活数据核验**：进程内表项 0–16 的 W/H/标签指针、三处浮点常量的活值。
4. **解密代码扫描**：`code2.py <pid> <base>` 对解密后的进程内 `.text` 做
   RIP 相对引用扫描（目标 = 表项/浮点/字符串 RVA），定位真正引用这些数据的
   解析函数与窗口夹取函数，并按 `cmp reg,5` + 紧邻 `jcc` 找门槛候选。
   `.pdata` 函数边界映射对解密代码同样有效（布局与文件一致）。
5. **干预**（仅在数据站点不足时）：对动态解析出的 `MoveWindow` 入口或上述
   解密函数打调试寄存器断点 / 内存热补丁（针对进程内存，不落盘）。

## 十、活进程核验结果（2026-11-11，Base98310 主菜单实测）

在实机运行中的 `SC2_x64.exe`（PID 18020，主菜单阶段）上完成了活数据核验。
结论：**27 处磁盘站点与游戏进程实际读取的数据一一对应，文件补丁在重启后必然生效；
第九节的代码级运行时路线对数据补丁不必要。**

### 1. 修正：引擎是常规 OS 加载模块

早前"模块列表为空/镜像手工映射"的判断是探针 bug（LDR 偏移取错、区域遍历地址
上限 `1<<44` 低于实际基址），并非进程行为：

- LDR `InLoadOrderModuleList` 第 0 项 = `SC2_x64.exe`，基址 **`0x7FF6C9E60000`**，
  与 PEB `ImageBaseAddress` 一致；共 142 个模块（kernel32/d3d9/… 齐全）。
- 先前误判的 `0x708D0000` 处 1.4MB 镜像是 **dbghelp.dll**（模块 #110），不是引擎。
- 进程内 PE 头 0x400 字节与磁盘文件一致，仅 PE+4（Machine）2 字节不同
  （文件 `0x8664`，内存 `0x0200`）——加载器改了内存头，无害。

### 2. 活数据逐字节核验（文件 == 进程，全部通过）

数据段（.data/.rdata）按原样从磁盘文件映射，`文件偏移 = RVA − 节差`
（.data 差 `0x1000`，.rdata 差 `0x800`）：

| 站点 | 文件偏移 | 进程地址 (base+RVA) | 核验结果 |
|---|---|---|---|
| 表项 e0–e5 宽/高 (144B) | `0x0391F860` | `+0x03920860` | W/H 逐字节一致（480x360…960x540）；仅 8B 标签指针被按基址正常重定位（`0x142E6F6xx` → `0x7FF6CCCCF6xx`） |
| 标签槽 e0–e5 (96B) | `0x02E6EE60` | `+0x02E6F660` | 逐字节一致（`@UI/480x360` … `@UI/960x540`） |
| AR 上限浮点 A | `0x02E7B480` | `+0x02E7BC80` | 一致 = 1.7777778f |
| AR 上限浮点 B（窗口夹取） | `0x02FB6AA0` | `+0x02FB72A0` | 一致 = 1.7777778f |
| AR 上限浮点 C（98370 同值） | `0x02D05F00` | `+0x02D06700` | 一致 = 1.7786459f |

活表 17 项完整读出：480x360 / 640x360 / 640x480 / 640x512 / 800x600 / 960x540 /
960x768 / 1024x768 / 1280x720 / 1280x960 / 1280x1024 / 1600x900 / 1600x1200 /
1920x1080 / 1920x1200 / 2560x1440 / 3840x2160；标签指针均指向活标签槽
（`base+0x02E6F660..0xB0`），与 ps1 的"槽基址 + 字符串长"约定完全吻合。
磁盘 exe SHA256 未变（原始值），当前运行的是未打补丁的原始数据——符合预期。

### 3. `.text` 观察（不影响数据补丁）

- 进程内 `.text`（base+`0x1000` 起 1MB）熵 7.8402（文件侧 ≈8.0）：部分就地解密/
  混合状态；另有 2 个 PAGE_EXECUTE 区域（共 ~3.95MB，`0x7FF6D1A10000` /
  `0x7FF6D1D10000`）承载解密后的可执行代码。
- 数据段（.data/.rdata）全程明文、与磁盘一致，是本 mod 补丁的落点，
  该结论已由上表实测锁定。

### 4. 活注入（live 模式）探测：`.data` 可写，`.rdata` 受保护

在运行进程上实测 `live`（不重启、进程内注入）：

| 站点组 | 节 | 实测 |
|---|---|---|
| 表项 e0–e5 宽/高 + 标签尾指针（18 处） | `.data` | **可写**（PAGE_READWRITE；写入 + 回读均成功） |
| 标签槽 e0–e5（6 处） | `.rdata` | **不可写** |
| 宽高比上限浮点 ×3 | `.rdata` | **不可写** |

`.rdata` 页（PAGE_EXECUTE_READ）的保护变更与写入三条路全被挡下：

1. `kernel32!VirtualProtectEx`（页对齐地址/长度）→ 错误 87（参数无效）；
2. `ntdll!NtProtectVirtualMemory` → 返回 `STATUS_SUCCESS`，但页面实际保护不变；
3. `WriteProcessMemory` 直接写 → 错误 998，任意延迟（0.1ms～1s 多档）均失败。

即 **98310 引擎对 `.rdata` 内的内存常量有运行时保护**（标签字符串与 16:9 宽高比
上限浮点都在这里）。只写 `.data` 只能改下拉表，宽高比上限仍为 1.7778，选中超宽
分辨率会被夹回——"半补丁"无意义，故完整内存注入在该版本不可行。

为此 ps1 的 `live` 已加固为 **先预检、后写入、全有或全无**：

- 预检（只读）：`VirtualQueryEx` 取各站点所在页保护，凡默认不可写的页先探测能否
  改为 `0x40`；任一页不能，则在**写入任何字节之前**中止并明确列出只读页地址；
- 写入中途失败时自动回滚已注入站点的原字节，保证进程不留在半补丁状态
  （另修复了旧 `Write-Mem` 未按页对齐调用 `VirtualProtectEx` 的缺陷）。

本机实测：`live` 正确检出 4 个只读页（1 个标签页 + 3 个浮点页）并中止，
退出码 2、零写入；执行后复验进程内全部 27 处与磁盘原始状态逐字节一致。

结论：**98310 的可靠路径是文件补丁（apply）+ 重启游戏**（引擎启动时从磁盘读入
新字节，内存保护不影响）；`live` 保留给其它版本，不适用时如实报告而非强行半注入。

### 5. 代码级引用交叉验证（活进程已解密代码，RIP 相对引用扫描）

对进程内**全部 5 个已提交区域**做 x64 RIP 相对引用扫描（`disp32 = 目标 − (指令尾)`，
numpy 向量化，逐条回读 disp 复核，剔除数据巧合——例如 `.rdata` 字符串
`"height\0"` 恰好构成指向 A 的假引用；`.data` 区内另有 4 处表基址旁的
结构相邻命中与 1 处指针表巧合，均非代码；`.data` 区内亦无指向任一常量的
绝对 QWORD 指针）：

| 常量 | 活地址 | 真代码引用 | 指令 |
|---|---|---|---|
| AR 上限 A（解析） | `0x7FF6CCCDBC80` | **1** | `F3 0F 10 15` `movss xmm2,[rip+d]` @`0x7FF6CB1C0C5E` |
| AR 上限 C（98370 同值） | `0x7FF6CCB66700` | **3** | `movss` @`0x7FF6CA07D833` / `0x7FF6CADCD64E` / `0x7FF6CB40F702` |
| 分辨率表基址 | `0x7FF6CD780860` | **1** | `48 8D 3D` `lea edi,[rip+d]` @`0x7FF6CB16223D` |
| AR 上限 B（窗口夹取） | `0x7FF6CCE172A0` | 0（主菜单阶段） | — |

结论：

- A 与 C 均被已解密代码以真实 SSE 加载引用，表基址被下拉表构建代码 `lea` 引用
  → 磁盘补丁落点确为引擎实际使用的数据，且与 98370 的"窗口夹取"常量（C 与其
  同值同类型）同源，方向与 98370 已验证先例一致。
- 表构建代码（`0x…16223D`）与 A 常量加载点（`0x…1C0C5E`）相距约 24KB，
  符合同一函数区间（下拉表构建 + AR 检查）。
- B 在主菜单阶段无引用：其所在代码区更可能**按需解密**（窗口缩放/渲染路径
  主菜单不执行，`.text` 密文→解密是切换器逐段做的），或 B 为冗余候选。
  无论哪种，常量都在执行时从（补丁后的）`.rdata` 页现取，补丁无法被绕过。
- 残余风险（无法事前排除）：若 98310 存在以整数运算硬编码 16:9、不经过这些
  浮点常量的代码路径，则可能出现"分辨率可选、窗口被夹"。届时按 98370 第五节
  IAT-hook（MoveWindow）路线兜底。

### 6. 事故：`Set-GameConfig` 的变量大小写冲突（2026-11-11 07:07 apply 后发现）

**现象**：apply 后 `Variables.txt` 从 149 行 CRLF 变成**单行**，每行之间被
`windowx=0` 顶替（153 处），所有键值虽在但结构全毁，游戏按行解析将丢失
`displaymode/width/height/windowx` 等全部显示键。

**根因**：PowerShell 变量名**不区分大小写**。`Set-GameConfig` 内
`$newline`（L433，换行符分隔符）与 `$newLine`（L442，逐行替换的临时变量）
是**同一个变量**。foreach 循环里每个命中的键行都会执行
`$newLine = "key=value"`，最后一次命中（原文件里最靠后的 `windowx=1279`）
把 `$newline` 覆盖成 `"windowx=0"`；随后 `($out -join $newline)` 用
`windowx=0` 当分隔符把所有换行替换掉。对原始文件（4 个键中 `windowx` 行
最后）恰好产生"每行后插 `windowx=0`"的精确形态，与事故文件逐字节吻合
（t1 重建 = 原文件 CRLF→`windowx=0`，仅 4 处键值更新差异）。

**审计**：全脚本变量名大小写冲突扫描（Python，139 个变量名）另见 9 组冲突，
逐一核对行号后均为 `param()` 声明与使用处大小写习惯差异（不同作用域或
同义绑定），无第二处双写；唯一的真冲突就是 `$newline/$newLine`。

**修复**：`$newLine` → `$updatedLine`（L442/443）。修复后 ps1 为 35,960 B、
UTF-8 BOM `EF BB BF`（edit 工具再次剥 BOM，按既定流程恢复）。

**事故处置**：exe 补丁本身不受影响（哈希 `83b775df…` 独立验证通过）；
配置从 `Variables.txt.sc2uw.bak` 恢复原样后用修复后的同一逻辑重写
（152 行 CRLF、7 键全部正确），事后校验脚本 4 项全 PASS。

**教训**：PS 脚本中任何"同词不同大小写"的变量名都是定时炸弹；本脚本此后
新增变量一律走该扫描（`varcollide.py`，产物目录 `sc2uw/`）。
